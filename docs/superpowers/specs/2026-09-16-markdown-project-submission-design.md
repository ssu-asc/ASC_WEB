# ASC Markdown Upload → ProjectDB Publish Design

**Date:** 2026-09-16
**Status:** Approved in chat for Phase 10 implementation

## Goal

Replace the member-facing Git/ProjectDB path/ref submission form with a simple Markdown file upload flow while keeping ProjectDB as the single long-term report repository for both individual and team projects.

Members submit:

- one required `.md` report file;
- an optional short description;
- an optional GitHub code repository URL.

Members do **not** enter ProjectDB paths, branches, tags, or commit SHAs. ASC_WEB stores the uploaded Markdown draft until staff approval. Approval publishes a server-generated, validated report into the existing `ssu-asc/ProjectDB` repository. Existing ProjectDB GitHub Actions then continue the Notion synchronization flow.

## Architecture Choice

Do not use Supabase Storage for Markdown drafts. Markdown reports are small text documents, so the browser reads the selected file as UTF-8 text and `submission-write` stores the text in Postgres. This keeps the member UX as a file upload while avoiding a Storage bucket, object RLS, storage quota management, signed URLs, and orphan-object cleanup.

ProjectDB remains the durable report system of record after approval.

```text
member selects report.md
        ↓
ASC_WEB reads UTF-8 text
        ↓
submission-write validates + stores draft text in submissions
        ↓
staff reviews submitted Markdown
        ├─ revision_requested → member uploads revised report.md
        └─ approved
              ↓
submission-admin generates trusted frontmatter/path
              ↓
GitHub Contents API writes report-01.md to ProjectDB main
              ↓
ProjectDB existing push workflow syncs changed report to Notion
```

## Scope Boundary

Phase 10 changes report submission and ProjectDB publication only. It does not change:

- semester-fixed teams;
- assignment scheduling;
- late classification;
- member roster/account management;
- Phase 8 resource links;
- Phase 9 staff secrets;
- the public ASC homepage.

PDF/PPTX/ZIP/assets are deferred. V1 accepts one Markdown text file only. Markdown may reference external images/URLs, but local bundled assets are not uploaded in Phase 10.

## Member Submission UX

`/member/submission?assignment=<id>` shows:

```text
[assignment title — read only]
제출 설명                    optional
보고서 (.md)                required
[report.md 선택]
선택한 파일명 · byte size
코드 GitHub 저장소          optional

[제출하기 / 수정 제출]
```

Removed from member UI:

- editable project title;
- ProjectDB repository input;
- ProjectDB Markdown path input;
- commit SHA / tag / branch input;
- report GitHub preview before approval.

The assignment title is authoritative and becomes the report project name.

### File rules

The browser performs fast feedback, and the server re-validates authoritatively:

- filename must end in `.md` case-insensitively;
- original filename is 1–128 characters and must be a basename only;
- UTF-8 text only;
- maximum encoded size: **262,144 bytes (256 KiB)**;
- file must contain at least one non-whitespace character;
- NUL bytes are rejected;
- a document whose first non-whitespace content starts with YAML frontmatter delimiter `---` is rejected;
- members are told that frontmatter is generated by ASC_WEB automatically.

The Markdown body is displayed to staff as escaped plain text (`<pre>` or equivalent), not injected as HTML.

## Database Migration 011

Add `202609160011_markdown_submission.sql`.

### submissions additions

```text
report_filename text null
report_markdown text null
report_bytes integer null
```

Rules:

- `report_filename` must be a safe `.md` basename when non-null;
- `report_bytes` must be 1..262144 when non-null;
- `octet_length(report_markdown) <= 262144` when non-null;
- new Phase-10 writes require all three Markdown draft fields;
- historical rows may retain null Markdown fields.

### publication fields

Existing fields remain but become nullable:

```text
report_repository_url
report_path
submitted_ref
```

Meaning after Phase 10:

- before successful ProjectDB publish: nullable;
- after successful publish:
  - `report_repository_url` = ProjectDB repository URL;
  - `report_path` = server-generated ProjectDB path;
  - `submitted_ref` = immutable Git commit SHA returned by GitHub.

When a previously approved submission is reopened and the member uploads a revised Markdown draft, these publication fields are cleared until the next successful publish.

Historical submissions without `report_markdown` keep the legacy review/sync behavior so migration 011 does not invalidate existing records.

## Submission Write Contract

`submission-write` accepts:

```text
assignment_id
summary
code_repository_url?   optional GitHub repo
report_filename
report_markdown
expected_version?      optimistic update
```

The server derives:

- title from `assignments.title`;
- individual owner or fixed semester team from current authenticated membership;
- report byte count from `TextEncoder`;
- submitted timestamps and state.

The old member-supplied fields are removed from the new browser API:

```text
report_repository_url
report_path
submitted_ref
```

The server must not trust a client-supplied project title or ProjectDB destination.

Existing rules remain:

- no submission before `opens_at`;
- post-deadline submission remains allowed;
- `first_submitted_at` remains immutable and drives late state;
- approved rows are member read-only until staff requests revision;
- team submissions remain one shared row per fixed semester team;
- stale member writes return conflict.

## ProjectDB Publication Model

Both individual and team reports publish to **the existing ProjectDB**, not a new repository.

### One assignment = one ProjectDB report

Portal assignments are standalone project deliverables, so each assignment maps to one ProjectDB report file:

```text
report_number: 1
filename: report-01.md
```

A revision/reapproval updates the same path rather than creating report-02, report-03, etc. The existing multi-report ProjectDB convention remains available for manually managed legacy projects.

### ProjectDB group/path

Team assignment:

```text
reports/{YYYY}/{team_segment}/{round_key}-{project_segment}/report-01.md
```

Individual assignment:

```text
reports/{YYYY}/개인/{member_id}-{round_key}-{project_segment}/report-01.md
```

Examples:

```text
reports/2026/A조/round-0002-web-scanner/report-01.md
reports/2026/개인/20231234-round-0001-malware-analysis/report-01.md
```

The server sanitizes path segments deterministically:

- Unicode letters/numbers, `_`, `-`, and Hangul are retained;
- whitespace collapses to `-`;
- `/`, `\\`, traversal components, control characters, and repeated punctuation are removed/replaced;
- a short fallback derived from assignment/member/team IDs is used if a segment becomes empty;
- generated paths never come from member input.

## Generated Frontmatter

Members upload body-only Markdown. `submission-admin` prepends frontmatter after staff approval.

Portal report example:

```yaml
---
source: "asc_web"
project_type: "individual"
project_name: "개인 프로젝트 1회차"
quad_name: "개인"
members: ["20231234_홍길동"]
report_number: 1
date: "2026-09-16"
status: "진행 중"
portal_submission_id: "<uuid>"
code_repository_url: "https://github.com/example/project"
---
```

Team report:

- `project_type: team`;
- `quad_name` is the fixed semester team name;
- `members` contains the confirmed team members at approval time.

Individual report:

- `project_type: individual`;
- `quad_name: 개인`;
- `members` contains exactly the submitting member.

Phase 10 does not invent contribution percentages or CL levels. Those fields are optional for `source: asc_web` reports. If the uploaded Markdown body includes a human-written contribution section, it remains in the report body.

`status` is `진행 중` for portal-generated reports because staff approval means the submitted deliverable is accepted; it does not necessarily assert that a longer-running project is globally complete.

## ProjectDB Compatibility Changes

ProjectDB changes must be backward compatible with all existing reports.

### validate_frontmatter.py

For legacy reports (`source` absent or not `asc_web`): current validation remains unchanged.

For `source: asc_web` reports:

Required:

```text
source
project_type
project_name
quad_name
members
report_number
date
status
portal_submission_id
```

Optional:

```text
cl_level
contributions
code_repository_url
```

Rules:

- `project_type` is `individual` or `team`;
- `report_number` remains valid integer metadata and Phase-10 generated reports use 1;
- if optional `cl_level` exists, validate the existing CL set;
- if optional `contributions` exists, validate using existing contribution rules;
- legacy validation semantics are unchanged.

The current five-segment path shape already accepts both new layouts because individual reports use `개인` as the group directory and encode the member ID in the project directory.

### sync_notion.py

- keep `project_name`, `quad_name`, `members`, report number, date, status and Git link behavior;
- only send `CL 등급` when `cl_level` exists instead of fabricating `CL1`;
- only send contribution text when contributions exist;
- skip submission-tracking checkbox updates when `project_type == individual`;
- team/legacy tracking behavior stays unchanged.

A direct portal GitHub Contents API commit to `main` already triggers the existing `reports/**/*.md` push workflow. The workflow has no `/week` PR comment for a portal direct commit, so tracking week remains empty; Notion project-report sync still runs.

## Approval / ProjectDB Sync

`submission-admin` preserves the existing durable approval model:

1. persist review state first;
2. if approved, claim a ProjectDB sync attempt;
3. publish the generated report to ProjectDB;
4. persist `synced` or `failed` independently;
5. approval is not rolled back by GitHub/Notion failure;
6. staff can retry ProjectDB sync.

For a Markdown-backed submission:

1. load assignment and owner/team identity server-side;
2. build trusted frontmatter + uploaded body;
3. compute trusted ProjectDB path;
4. GET existing ProjectDB file on target branch;
5. PUT create/update via GitHub Contents API;
6. read returned commit SHA;
7. persist `report_repository_url`, `report_path`, `submitted_ref`, sync state and timestamp.

If the path already exists, the server supplies the existing blob SHA so reapproval updates the same file.

Legacy submissions with no `report_markdown` continue using the previous supplemental archive path behavior.

## Staff Review UX

The staff round-first submissions view adds Markdown draft inspection:

- uploaded filename;
- byte size;
- escaped Markdown body preview;
- optional code repository link;
- existing late/status/review-note controls;
- after successful publish, link to the ProjectDB report at the immutable commit SHA;
- if publish failed, show existing retry action/error.

Staff must review the exact Markdown body stored in the submission row; approval must not fetch untrusted content from a member-controlled mutable URL.

## Security

- no member chooses a ProjectDB path or commit target;
- no GitHub write token reaches the browser;
- Markdown is stored and previewed as text, not unsanitized HTML;
- server validates UTF-8 text length/filename/frontmatter rules;
- ProjectDB write still requires the server-side minimal GitHub token;
- RLS continues to restrict submission rows by owner/team/staff;
- approved submissions remain immutable to members;
- optimistic versions prevent stale overwrite/review;
- generated frontmatter uses trusted DB identity/team/assignment values.

## Free-Cost Constraint

Phase 10 adds no paid storage service. Markdown drafts live in existing Supabase Postgres and approved reports live in the existing GitHub ProjectDB repository. No new VPS, object-storage provider, or paid GitHub repository is required.

## Out of Scope

- PDF/PPTX/ZIP submission;
- multiple file upload;
- images/assets uploaded with Markdown;
- WYSIWYG/Markdown editor;
- arbitrary ProjectDB path selection;
- member-controlled Git branch/tag/ref;
- automatic creation of per-project code repositories;
- code repository mirroring;
- new ProjectDB repository;
- changing public homepage projects data during Phase 10.
